# 编写技术方案

为活跃变更编写 `design.md`，基于对目标代码区域的实际调研来做架构决策。

**开始时宣告：** "正在使用 qx-dev-design 为变更 [名称] 编写技术方案。"

## 何时使用

- proposal 已写好，准备定义"怎么做"
- 简单变更可跳过，直接从 proposal 到 `/qx-dev-plan`

## 前提

`docs/changes/<name>/proposal.md` 必须存在。

## 流程

### 步骤 1：阅读输入

1. 阅读 `proposal.md` 和所有 specs（如有）
2. 阅读 `docs/system-map.md` 了解现有系统关系
3. 阅读 CLAUDE.md 获取项目特定的架构模式和框架规则

### 步骤 2：代码区域调研

**在做任何设计决策之前，先深入阅读目标代码区域。**

根据 proposal 识别需要修改/交互的代码区域，然后：

**2a. 探索目标区域结构：**
- 列出目标目录/模块的文件结构
- 阅读核心文件，理解现有架构模式
- 识别命名规律、组织惯例

**2b. 提取现有模式和约定：**
- 已有类似功能是怎么实现的？（找可参考的模板）
- 数据模型怎么组织的？（继承层级、所有权关系）
- 消息/事件怎么流转的？
- 有哪些框架属性/注解在使用？

**2c. 识别约束和边界：**
- 程序集边界和依赖方向（Model/Share vs Server vs Hotfix）
- 哪些分析器规则会触发？（ET0002/ET0004/ET0013/ET0031/ET0032 等）
- 跨进程/跨线程的边界在哪？
- 序列化约束（哪些类型可序列化）

**2d. 影响扫描：**

根据变更类型执行定向扫描：

| 变更类型 | 扫描内容 |
|----------|----------|
| 数据模型/Component | 所有权声明、引用此模型的逻辑模块、创建/访问调用点、事件处理器 |
| 消息/协议 | 协议定义、Handler 类、发送/调用点、消息链路 |
| 事件 | 事件定义、处理器/监听器、发布/分发点、运行进程 |
| Entity/数据结构 | 所有权声明、工厂方法、序列化影响 |
| 数值/配置 | 常量定义、读写用法、计算链、显示代码 |

**输出：** 记录发现的模式、约束和影响到 design.md 中。

### 步骤 3：起草 design.md

基于步骤 1-2 的理解，起草技术方案：

```markdown

<!-- 背景和当前状态 -->

## 目标 / 非目标

**目标：**
<!-- 此设计旨在达成什么 -->

**非目标：**
<!-- 明确不在范围内的内容 -->

## 代码调研发现

<!-- 目标区域使用的架构模式、命名惯例、组织方式 -->

|-----------|----------|------|
| [路径] | 直接修改/间接影响 | [具体影响] |
```

### 步骤 4：建议下一步

"/qx-dev-plan — 编写实施计划"

## 核心原则

- **先读代码再做决策** — 设计必须基于对现有代码的实际理解，而非想象
- **聚焦"为什么选 X 而非 Y"** — 记录决策过程，而非逐行代码
- **检查 system-map.md** — 在设计期间引用持久化系统关系图
- **约束前置** — 在决策之前就识别框架约束，避免设计出违反规则的方案

## 相关 Skills

- **qx-dev-create** — 创建变更和 proposal（本 Skill 的前置）
- **qx-dev-plan** — 将 design 转化为实施计划（本 Skill 的后续）
- **qx-dev-explore** — 如果需要更自由的探索，可先用 explore 再回到 design
- **qx-compound** — 在变更完成后更新系统图
