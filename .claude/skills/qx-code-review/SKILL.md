# 代码审查（Code Review）

## 概述

调度 code-reviewer 子 Agent（以及可选的 security-reviewer）在问题扩散之前发现它们。

**核心原则：** 早审查，勤审查。

**启动时宣告：** "正在使用 qx-code-review 审查实现。"

## 何时请求审查

**必须：**
- 完成重大功能或计划任务组后
- 合并到主分支前
- 完成变更后（`/qx-dev-change verify` 会触发此操作）

**可选但有价值：**
- 卡住时（换个视角）
- 重构前（基线检查）
- 修复复杂 Bug 后
- 多 Agent 执行中每个任务完成后

## 审查维度

QX 代码审查最多支持三个审查维度：

| 维度 | Agent | 何时 |
|------|-------|------|
| **代码质量 + 计划对齐 + 框架合规** | `code-reviewer` | 始终（必须） |
| **安全** | `security-reviewer` | 当网络/认证/输入处理发生变更时 |

### 自动检测规则

**框架规则审查在以下变更时触发：**
- 核心框架模式（阅读 CLAUDE.md 了解项目特定模式）
- 数据模型定义或组件结构
- 系统/逻辑类
- 消息处理器或协议文件
- 框架特定目录中的文件

**安全审查在以下变更时触发：**
- 网络消息处理器
- 会话管理代码
- 进程间或服务间通信
- 输入验证或序列化
- 跨边界通信

## 如何请求审查

**1. 获取 git SHA：**
```bash
BASE_SHA=$(git rev-parse HEAD~1)  # 或与 main 的 merge-base
HEAD_SHA=$(git rev-parse HEAD)
```

**2. 调度 code-reviewer Agent：**

使用 Agent 工具，`subagent_type: "code-reviewer"`，提供：
- 实现了什么（描述）
- 计划或需求引用
- Git 范围（BASE_SHA..HEAD_SHA）

**3. 可选地并行调度安全审查员**

当安全敏感代码发生变更时，使用 Agent 工具，`subagent_type: "security-reviewer"`

**4. 根据反馈采取行动：**
- 立即修复 **Critical（严重）** 问题
- 在继续之前修复 **Important（重要）** 问题
- 记录 **Suggestion（建议）** 问题留待后续处理
- 如果审查员判断有误，用理由反驳

## 代码审查模板

调度 code-reviewer Agent 时，提供以下上下文：

```
你正在审查代码变更以确保生产就绪。

**实现内容:** {DESCRIPTION}
**需求/计划:** {PLAN_REFERENCE}
**Git 范围:** {BASE_SHA}..{HEAD_SHA}

重要: 阅读项目的 CLAUDE.md 了解框架特定的规则和约定。

审查 git diff 并检查：

## 审查清单

### 代码质量
- 关注点分离是否清晰？
- 错误处理是否恰当？
- 类型安全？
- 是否遵循 DRY（不重复）原则？
- 边界情况是否处理？

### 框架合规
- 阅读 CLAUDE.md 了解项目特定规则
- 是否遵循所有框架编码约定？
- 文件/模块放置是否符合项目架构？
- 是否有必需的属性/注解？
- 是否运行了构建/编译验证命令？

### 架构
- 设计决策是否合理？
- 是否考虑了可扩展性？
- 性能影响如何？
- 并发模型是否合适？

### 测试
- 测试是否真正测试了逻辑（而非只是 mock）？
- 是否覆盖了边界情况？
- 所有测试是否通过？

### 需求
- 是否满足所有计划需求？
- 实现是否匹配规格？
- 是否有范围蔓延？
- 如适用，是否运行了代码生成步骤？

## 输出格式

### 优点
[哪些做得好？用 file:line 引用具体说明。]

### 问题

#### Critical（严重 - 必须修复）
[Bug、安全问题、数据丢失风险、功能损坏、框架规则违反]

#### Important（重要 - 应当修复）
[架构问题、缺失功能、错误处理不当、测试缺口]

#### Suggestion（建议 - 最好能改）
[代码风格、优化、文档改进]

**每个问题包含：**
- File:line 引用
- 问题所在
- 为何重要
- 如何修复（如果不明显）

### 评估
**是否可以合并？** [是 / 否 / 修复后可以]
**理由：** [1-2 句话]
```

## 问题严重级别指南

| 严重级别 | 示例 | 处理方式 |
|----------|------|----------|
| **Critical** | 框架规则违反、安全漏洞、数据丢失风险、功能损坏 | 必须在继续之前修复 |
| **Important** | 缺少错误处理、测试缺口、模块放置错误、架构问题 | 应在合并前修复 |
| **Suggestion** | 命名约定、代码组织、文档 | 记录留待后续 |

## 工作流示例

```
[刚完成任务 2: 添加 BuffComponent System]

你: 让我请求代码审查。

BASE_SHA=$(git merge-base HEAD main)
HEAD_SHA=$(git rev-parse HEAD)

[调度 code-reviewer Agent]
  描述: BuffComponent，含添加/移除/查询和持续时间计时器
  计划: docs/changes/buff-system/plan.md, Task 2
  范围: a7981ec..3df7661

[code-reviewer 返回]:
  优点: 数据和逻辑分离清晰
  框架合规: 所有框架规则均符合
  问题:
    Important: Destroy 处理器未取消活跃计时器
    Suggestion: 考虑使用现有 numeric 系统进行属性修改
    Suggestion: 考虑添加生命周期方法注解
  评估: 修复后可合并

你: [修复 Destroy 中的计时器清理]
[继续任务 3]
```

## 与工作流的集成

**多 Agent 执行（`/qx-dev-exec`）：**
- 每个任务组后审查
- 在问题复合之前发现它们
- 在进入下一组之前修复

**变更生命周期（`/qx-dev-change verify`）：**
- 完整的三维度审查
- 作为验证阶段的一部分

**临时开发：**
- 合并前审查
- 卡住时审查

## 危险信号

**绝不：**
- 因为"很简单"就跳过审查
- 忽视 Critical 问题
- 在 Important 问题未修复的情况下继续
- 与合理的技术反馈争论
- 在核心框架代码变更时跳过框架规则审查

**如果审查员判断有误：**
- 用技术理由反驳
- 展示证明其有效的代码/测试
- 请求澄清
