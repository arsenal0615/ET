# 系统影响分析（System Impact Analysis）

## 概述

通过扫描代码库关系 — 数据模型、逻辑模块、消息、事件及其连接 — 来分析拟议变更的影响。生成结构化影响报告，为规划提供信息并减少意外损坏。

**核心原则：** 在开始修改代码之前，先理解爆炸半径。

**开始时宣告：** "正在使用 qx-dev-impact 分析 [拟议变更] 的影响。"

## 何时使用

- 在实现涉及共享系统的变更之前
- 当 `/qx-meeting` 识别出潜在的跨系统影响时
- 当规划一个你不完全熟悉的系统的工作时
- 当变更涉及修改协议消息、数据模型结构或事件流时

## 两层分析模型

QX 使用两层系统分析方法：

### 第一层：持久化系统图
**文件：** `docs/system-map.md`
**粒度：** 中等（Component/系统组）
**更新者：** 每次变更完成后由 `/qx-compound` 更新

系统图提供了现有内容和系统连接方式的快速概览。它是在项目生命周期中持续维护的活文档。

### 第二层：按需影响分析（本 Skill）
**粒度：** 细粒度（具体文件、字段、消息链）
**触发方式：** `/qx-dev-impact` 或被其他 skills 内部调用
**输出：** 针对特定拟议变更的一次性分析报告

## 流程

### 步骤 1：定义变更范围

询问用户（或从变更提案中读取）：
- 正在变更什么系统或组件？
- 什么类型的变更？（新增/修改/删除数据模型、消息、事件等）
- 动机是什么？（有助于识别我们需要保护什么）

### 步骤 2：阅读系统图

阅读 `docs/system-map.md` 了解已知的系统关系。

如果系统图尚不存在，记录下来并直接进行代码库扫描。

### 步骤 3：阅读项目规则

阅读项目的 CLAUDE.md 和 MEMORY.md 了解：
- 框架特定的模式和约定
- 需要搜索的关键属性/注解
- 模块/程序集组织
- 可能受影响的代码生成步骤

### 步骤 4：扫描代码库关系

根据变更内容执行定向扫描。将扫描模式适配项目框架（阅读 CLAUDE.md 获取细节）：

**如果变更数据模型/Component：**
1. 查找所有权声明 — 哪个父 Entity 拥有它？
2. 查找所有引用此数据模型的逻辑模块
3. 查找所有创建/实例化调用点
4. 查找所有读取/访问调用点
5. 查找引用此数据模型的事件处理器

**如果变更消息/协议：**
1. 查找协议定义
2. 查找此消息的所有 Handler 类
3. 查找所有发送/调用点
4. 追踪消息链穿过系统层
5. 如果是请求/响应对，查找响应类型

**如果变更事件：**
1. 查找事件定义
2. 查找所有事件处理器/监听器
3. 查找所有事件发布/分发点
4. 检查此事件在哪些进程/线程中运行

**如果变更 Entity/数据结构（父子关系）：**
1. 查找所有权声明
2. 查找创建/实例化调用
3. 查找构造此 Entity 的工厂方法
4. 检查序列化影响

**如果变更数值/配置属性：**
1. 查找常量/类型定义
2. 查找此属性的所有读写用法
3. 查找产生/消费此值的计算
4. 检查展示此值的显示代码

### 步骤 5：分类影响

对每个受影响区域进行分类：

| 影响级别 | 标准 |
|----------|------|
| **直接** | 直接引用被变更元素的代码 |
| **间接** | 依赖直接引用的代码（第二度） |
| **潜在** | 共享同一系统边界的代码（可能受影响） |

### 步骤 6：生成影响报告

```markdown
# 影响分析: [变更描述]

## 变更摘要
- **目标:** [被变更的 Component/消息/事件]
- **类型:** [新增/修改/删除]
- **动机:** [为什么做此变更]

## 直接影响
| 文件 | 元素 | 影响 |
|------|------|------|
| [路径] | [类/方法] | [变更内容] |

## 间接影响
| 文件 | 元素 | 影响 |
|------|------|------|
| [路径] | [类/方法] | [潜在效果] |

## 消息链影响
```
[追踪: 逐层展示受影响的消息]
```

## 跨系统依赖
- [系统 A] 通过 [机制] 依赖 [被变更元素]
- [系统 B] 为 [目的] 读取 [被变更数据]

## 风险评估
| 风险 | 级别 | 缓解措施 |
|------|------|----------|
| [风险描述] | 高/中/低 | [如何缓解] |

## 推荐测试覆盖
- [ ] [测试场景 1]
- [ ] [测试场景 2]

## 需要修改的文件
1. [文件路径] — [变更内容]
2. [文件路径] — [变更内容]
```

### 步骤 7：呈现和建议

呈现分析摘要：

```
影响分析完成 — [变更描述]

直接影响: [N] 个文件
间接影响: [N] 个文件
风险级别: [高/中/低]

关键风险:
1. [首要风险]
2. [次要风险]

建议: [继续 / 谨慎继续 / 重新考虑方案]
```

提供下一步选项：
- "继续制定实施计划？（`/qx-dev-plan`）"
- "要我在 [特定区域] 深入扫描吗？"
- "要用这些发现更新系统图吗？"

## 扫描模式速查

> **注意：** 阅读项目的 CLAUDE.md 获取项目特定的模式、属性名称和约定。以下模式是通用示例 — 请适配你项目的框架。

| 查找目标 | 通用方法 |
|----------|----------|
| 数据模型所有者 | 搜索所有权/父级声明属性 |
| 子级关系 | 搜索子级/包含声明属性 |
| 逻辑模块 | 搜索引用目标类型的类 |
| 数据模型用法 | 搜索目标类型的创建和访问调用 |
| 消息处理器 | 搜索匹配消息名称的 Handler 类 |
| 事件处理器 | 搜索事件监听器/订阅者注册 |
| 事件发布者 | 搜索事件发布/分发调用 |
| RPC 调用者 | 搜索使用请求类型的远程调用 |
| 工厂方法 | 搜索工厂/创建模式 |

## 核心原则

- **先扫描再规划** — 影响分析为实施计划提供信息
- **先广度后深度** — 从直接引用开始，然后向外追踪
- **分类，而非仅列举** — 直接 vs 间接 vs 潜在的区分很重要
- **风险驱动测试** — 影响越大的区域需要更多测试覆盖
- **活的知识** — 为新发现建议更新系统图
