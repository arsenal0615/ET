# 系统化调试（Systematic Debugging）

## 概述

随机修复浪费时间并引入新 Bug。快速补丁掩盖底层问题。

**核心原则：** 在尝试修复之前，必须先找到根因。对症治标是失败的表现。

**违背此流程的字面含义，就是违背调试的精神。**

## 铁律

```
没有根因调查，就不能提出修复方案
```

如果你没有完成阶段 1，就不能提出修复方案。

## 何时使用

适用于任何技术问题：
- 测试失败
- 生产环境 Bug
- 异常行为
- 性能问题
- 构建失败
- 集成问题

**以下情况尤其需要使用：**
- 时间紧迫时（紧急情况让人倾向于猜测）
- "一个快速修复"看起来很明显时
- 你已经尝试了多次修复时
- 上一次修复没有生效时
- 你没有完全理解问题时

**以下情况不要跳过：**
- 问题看起来很简单（简单的 Bug 也有根因）
- 你很赶时间（急躁保证返工）
- 领导要求"立刻修好"（系统化比反复试错更快）

## 四个阶段

你必须完成每个阶段后才能进入下一个阶段。

### 阶段 1：根因调查

**在尝试任何修复之前：**

1. **仔细阅读错误信息**
   - 不要跳过错误或警告
   - 它们通常包含确切的解决方案
   - 完整阅读堆栈跟踪
   - 记录行号、文件路径、错误代码

2. **稳定复现**
   - 你能可靠地触发它吗？
   - 确切的步骤是什么？
   - 每次都会发生吗？
   - 如果无法复现 → 收集更多数据，不要猜测

3. **检查最近的变更**
   - 什么变更可能导致了这个问题？
   - Git diff，最近的提交
   - 新依赖、配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统有多个组件时（客户端 → 服务端，或服务 → 服务）：**

   **在提出修复方案之前，添加诊断埋点：**
   ```
   对每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置的传播
     - 检查每一层的状态

   运行一次以收集证据，确定在哪里断裂
   然后分析证据，定位故障组件
   然后调查该特定组件
   ```

   **示例（多层请求链）：**
   ```
   // 第 1 层：客户端发送请求
   Log("=== Client sending LoginRequest: Account={account} ===");

   // 第 2 层：网关接收
   Log("=== Gateway received LoginRequest: SessionId={id} ===");

   // 第 3 层：网关转发到后端
   Log("=== Gateway forwarding to AuthService: TargetId={serviceId} ===");

   // 第 4 层：后端处理
   Log("=== AuthService processing login: Account={account} ===");
   ```

   **这揭示了：** 哪一层失败了（Client → Gateway 正常, Gateway → AuthService 失败）

5. **追踪数据流**

   **当错误在调用栈深处时：**

   参见本目录中的 `root-cause-tracing.md` 获取完整的反向追踪技术。

   **简要版本：**
   - 错误值从哪里产生的？
   - 什么调用了这个方法并传入了错误值？
   - 持续向上追踪直到找到源头
   - 在源头修复，而非在症状处修复

### 阶段 2：模式分析

**在修复之前找到模式：**

1. **查找正常工作的示例**
   - 在同一代码库中找到类似的正常代码
   - 什么类似的功能是正常工作的？

2. **与参考实现对比**
   - 如果在实现某个模式，完整阅读参考实现
   - 不要略读 - 逐行阅读
   - 在应用之前完全理解该模式

3. **识别差异**
   - 正常工作的和出问题的之间有什么区别？
   - 列出每一个差异，无论多小
   - 不要假设"那不可能有影响"

4. **理解依赖关系**
   - 它需要哪些其他组件？
   - 什么设置、配置、环境？
   - 它做了哪些假设？

### 阶段 3：假设与测试

**科学方法：**

1. **建立单一假设**
   - 清晰陈述："我认为 X 是根因，因为 Y"
   - 写下来
   - 要具体，不要模糊

2. **最小化测试**
   - 做最小的可能变更来测试假设
   - 一次只改一个变量
   - 不要同时修复多个问题

3. **继续之前先验证**
   - 生效了？是 → 阶段 4
   - 没生效？建立新假设
   - 不要在上面叠加更多修复

4. **当你不知道时**
   - 说"我不理解 X"
   - 不要假装知道
   - 请求帮助
   - 进一步研究

### 阶段 4：实施

**修复根因，而非症状：**

1. **创建失败的测试用例**
   - 最简单的可能复现
   - 尽可能自动化测试
   - 修复前必须有
   - 使用 `qx-tdd` Skill 编写正确的失败测试

2. **实施单一修复**
   - 解决已确定的根因
   - 一次只改一处
   - 不要"既然在这里了顺便改改"
   - 不要捆绑重构

3. **验证修复**
   - 测试现在通过了？
   - 没有破坏其他测试？
   - 问题确实解决了？

4. **如果修复没有生效**
   - 停下来
   - 计数：你已经尝试了几次修复？
   - 如果 < 3 次：返回阶段 1，用新信息重新分析
   - **如果 >= 3 次：停下来质疑架构（下面的第 5 步）**
   - 不要在没有架构讨论的情况下尝试第 4 次修复

5. **如果 3 次以上修复失败：质疑架构**

   **表明架构问题的模式：**
   - 每次修复都暴露出不同位置的新共享状态/耦合/问题
   - 修复需要"大规模重构"才能实施
   - 每次修复在其他地方产生新症状

   **停下来质疑根本问题：**
   - 这个模式在根本上是合理的吗？
   - 我们是否"因为惯性而一直坚持"？
   - 应该重构架构还是继续修复症状？

   **在尝试更多修复之前与你的人类伙伴讨论**

   这不是假设失败 — 这是架构错误。

## 项目特定调试

阅读项目的 CLAUDE.md 和 MEMORY.md 获取框架特定的调试指南：

- **常见错误模式** — 框架特定的错误及其典型原因
- **组件/系统问题** — 与项目架构模式相关的问题
- **消息/网络问题** — 通信和序列化问题
- **并发问题** — 线程、异步和同步问题
- **构建/编译问题** — 构建工具和编译器错误
- **配置/数据问题** — 配置加载和数据验证问题
- **调试工具** — 项目特定的调试工具和命令

**始终首先检查 CLAUDE.md** — 项目的指令文件包含框架规则、常见陷阱和验证命令，这些对诊断项目特定问题至关重要。

## 危险信号 - 停下来遵循流程

如果你发现自己在想：
- "先快速修一下，以后再调查"
- "试着改一下 X 看看能不能行"
- "同时改多处，跑测试"
- "跳过测试，我手动验证"
- "大概是 X 的问题，让我修一下"
- "我没完全理解但这可能有用"
- "模式说要 X 但我换个方式"
- "主要问题如下：[列出修复方案但没有调查]"
- 在追踪数据流之前就提出解决方案
- **"再试一次修复"（已经试了 2 次以上）**
- **每次修复都暴露出不同位置的新问题**

**以上全部意味着：停下来。返回阶段 1。**

**如果 3 次以上修复失败：** 质疑架构（见阶段 4.5）

## 常见合理化借口

| 借口 | 现实 |
|------|------|
| "问题很简单，不需要流程" | 简单问题也有根因。流程对简单 Bug 很快。 |
| "紧急情况，没时间走流程" | 系统化调试比胡乱猜测试错更快。 |
| "先试这个，再调查" | 第一次修复树立了模式。从一开始就做对。 |
| "确认修复有效后再写测试" | 未测试的修复不可靠。先写测试证明它。 |
| "同时修多处节省时间" | 无法隔离哪个生效了。会引入新 Bug。 |
| "参考太长了，我改编一下" | 部分理解保证出 Bug。完整阅读。 |
| "我看到问题了，让我修" | 看到症状 ≠ 理解根因。 |
| "再试一次修复"（在 2 次以上失败后） | 3 次以上失败 = 架构问题。质疑模式，而非继续修复。 |

## 速查表

| 阶段 | 关键活动 | 成功标准 |
|------|----------|----------|
| **1. 根因** | 读错误信息、复现、检查变更、收集证据 | 理解是什么以及为什么 |
| **2. 模式** | 找正常示例、对比 | 识别差异 |
| **3. 假设** | 建立理论、最小化测试 | 确认或建立新假设 |
| **4. 实施** | 创建测试、修复、验证 | Bug 解决，测试通过 |

## 当流程显示"找不到根因"时

如果系统化调查显示问题确实是环境相关、时序依赖或外部原因：

1. 你已经完成了流程
2. 记录你调查了什么
3. 实施适当的处理（重试、超时、错误消息）
4. 添加监控/日志用于后续调查

**但是：** 95% 的"找不到根因"情况是调查不完整。

## 辅助技术

以下技术是系统化调试的一部分，位于本目录中：

- **`root-cause-tracing.md`** - 通过调用栈反向追踪 Bug 以找到原始触发点
- **`defense-in-depth.md`** - 在找到根因后在多个层面添加验证
- **`condition-based-waiting.md`** - 用条件轮询替代硬编码超时

**相关 Skills：**
- **qx-tdd** - 用于创建失败的测试用例（阶段 4，步骤 1）
- **qx-verify** - 在宣称成功之前验证修复是否生效

## 实际影响

来自调试实践的数据：
- 系统化方法：15-30 分钟修复
- 随机修复方法：2-3 小时反复折腾
- 一次修复成功率：95% vs 40%
- 引入新 Bug：几乎为零 vs 经常发生
